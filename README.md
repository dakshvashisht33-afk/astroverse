# AstroVerse

AstroVerse is an early-stage astrology dashboard. Chart and timing features are prototypes; timing windows are explicitly approximate, and unknown birth times use a noon estimate for planetary positions while omitting houses. Astrology content is for entertainment and self-reflection, not professional advice.

## Backend setup

Use Python 3.10 or newer:

```sh
cd backend
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\\Scripts\\activate
pip install -r requirements.txt
cd ..
uvicorn backend.main:app
```

The backend uses a local SQLite database by default (`astroverse.db`). Copy `.env.example` to `.env` in the project root to set a local secret and frontend origins. Set `DATABASE_URL` to a PostgreSQL URL to use PostgreSQL. Use a strong random `SECRET_KEY` and production `CORS_ORIGINS` before deployment. The API is available at `http://localhost:8000`. The basic command above runs without the file watcher. For auto-reload, keep the virtual environment outside `backend/` and use `--reload --reload-dir backend`.

## Astro AI setup

Astro AI supports Google Gemini and OpenAI from the backend. For a Google AI Studio key, set `AI_PROVIDER=gemini`, `GEMINI_API_KEY=...`, and optionally `GEMINI_MODEL` in the project-root `.env`. `GEMINI_FALLBACK_MODELS` is a comma-separated ordered fallback list used for transient busy, timeout, unavailable-model, and empty-response failures. For OpenAI, set `AI_PROVIDER=openai`, `OPENAI_API_KEY=...`, and optionally `OPENAI_MODEL`. Never put provider keys in `frontend/.env` or a `NEXT_PUBLIC_*` variable. Restart the backend after editing `.env`. The backend uses the `certifi` CA bundle for verified HTTPS requests, which helps Python installations without a configured system CA path. Without a key, the rest of the app works and chat displays a setup message. The AI receives chart placements and current transits for personalization, but the backend does not include the account name, exact birth date, birthplace, or coordinates in its chart context. Recent conversation turns are sent with each request; messages are not stored in the app database.

## Frontend setup

In another terminal:

```sh
cd frontend
npm install
npm run dev
```

Open `http://localhost:3000`. Set `NEXT_PUBLIC_API_URL` if the backend is hosted somewhere else. The onboarding city suggestions use the public Photon search service (OpenStreetMap data), so place searches need an internet connection. Selecting a suggestion fills the coordinates and timezone automatically.

## Deploy to Render and Vercel

The repository is configured as a monorepo: Render serves the FastAPI backend from the project root using `render.yaml`, and Vercel serves the Next.js app with its project root set to `frontend/`.

1. Push this project to a private GitHub repository. `.env`, local databases, virtual environments, and build artifacts are excluded; never commit API keys.
2. In Render, create a PostgreSQL database in the Singapore region and note its **internal** connection string. Free Render Postgres expires after 30 days, so use a paid database for persistent user accounts and profiles.
3. In Render, create a Blueprint from the repository and set `DATABASE_URL` to that PostgreSQL connection string and `GEMINI_API_KEY` to the key from your local `.env`. Keep `SECRET_KEY` generated by Render. The backend deploys at its `/health` endpoint when ready.
4. In Vercel, import the same repository and set **Root Directory** to `frontend`. Add `NEXT_PUBLIC_API_URL` with the Render backend URL, including `https://` and no trailing slash, then deploy.
5. In Render, update `CORS_ORIGINS` to the exact Vercel production URL (for example `https://astroverse-yourname.vercel.app`). The Blueprint also allows Vercel preview URLs. Save the change and redeploy the backend.
6. Open the Vercel URL and verify signup, login, saved birth profiles, chart loading, and Astro AI. Provider keys belong only in Render environment variables; do not add them to Vercel.

For a deployable, persistent service, configure a paid Render Postgres plan before inviting users. Render's free web service may spin down while idle, and its free Postgres has a 30-day lifetime and no backups. See [Render's free plan limitations](https://render.com/docs/free).

## Current limits

- Astro AI requires a server-side Gemini or OpenAI API key and provider access; without that configuration, the endpoint returns a clear setup message.
- Checkout and payment webhooks are disabled until a real provider and webhook signature verification are configured.
- Astrology readings and Ashtakoota compatibility are traditional, interpretive outputs. Their conventions and limitations are shown in the interface; they are not guaranteed predictions or relationship advice.
- Compatibility currently requires both birth profiles. The partner's timezone and decimal latitude/longitude must be supplied; a place lookup is not part of that form yet.
- Quick numerology uses Pythagorean letter mapping and digit reduction only. Other numerology traditions, baby-name suggestions, name/Moon-only matching, festival calendar, and full interpretive reports remain to be built.
- Divisional charts and daily timing use documented calculation conventions but still warrant review by a qualified Vedic astrology practitioner before users rely on them for consequential decisions.
